# 个人项目反思日志

项目：云购生活新零售数仓与经营分析系统　成员：孙浩瑜　日期：2026-11-17

## 一、技术维度

### 掌握扎实的部分

1. **Docker Compose 多服务编排**：从第 1 周三容器起步，到第 4 周六服务 + healthcheck 依赖链 + `.env` 密钥注入，能够独立完成企业级编排；对"镜像拉取失败走镜像源、bind mount 源缺失导致容器循环崩溃"这类故障已形成排障直觉。
2. **Hive 数仓分层建模**：ODS→DWD→DWS→ADS 各层职责边界清晰，星型模型（事实表 + 维表 + 日分区）从建模到 ORC/Snappy 落地全程亲手完成；理解了为什么 ADS 要物化小表——仪表板 8 图表并发压测时，直接查明细会触发 Tez 并发故障。
3. **数据勾稽意识**：养成了"每一层都要对得上"的习惯，最终联调时 GMV 在 DWD、ADS KPI、区域合计、ClickHouse、大屏接口五处全部精确一致（36,256,326.33）。

### 仍需加强的部分

1. **流式/增量处理**：本项目是全量批处理，对 Kafka/Flink 实时链路没有实战，这是与生产数仓的最大差距；
2. **权限与治理**：Ranger/Sentry 级别的细粒度权限、数据血缘工具未涉及；
3. **调度系统**：ETL 靠手动按序执行，DolphinScheduler/Airflow 调度编排是下一步学习重点。

## 二、协作维度

1. **Git 工程化**：完整走过 feature 分支 → PR → Review → 冲突解决 → 合并 → tag 的闭环。印象最深的是 README 阶段行合并冲突：两边都要保留时不能简单取一边，要手工融合双方信息再提交。
2. **AI 协同的角色定位**：五周实践让我明确了一条边界——AI 负责"生成与草拟"（脚本、文档初稿、SQL 方案），我负责"决策与核验"（口径确认、XGBoost 过拟合弃用、密钥不入库的安全把关）。每一条 AI 产出都经过人工验证才入库，协同日志留痕了 31 条真实记录。
3. **文档即协作**：指标口径文档让"品类销售额 4.53 亿 vs GMV 3,625 万"这类容易被误判为 Bug 的口径差异有了书面依据；联调核对清单则让验收有据可查。
