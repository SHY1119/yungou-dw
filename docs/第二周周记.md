# 第二周周记

- 团队：云购数智队　成员：孙浩瑜　时间：2026-11-02 ~ 2026-11-06
- 本周主题：数据清洗进阶 · Hive 四层数仓建模 · 探索性分析

## 一、本周完成的工作

本周在第一周"能用"的基础上，把数仓从"数据搬进来了"推进到"数据可信、可分析"。

**清洗进阶。** 周一先用画像扫描脚本摸清了 6 张 ODS 表全部枚举字段的真实取值分布——gender 有 8 种写法、order_status 有 12 种、behavior_type 有 10 种，其中还混着 1/2/3/4 这种数据字典里查不到的数字码。在此基础上写了枚举标准化脚本，把 8 个字段全部收敛到规范值域；异常值方面处理了负金额、超大金额、年龄 200、数量 -5 等，最终统计：17,168 项脏数据修复 16,975 项，整体修复率 98.87%。

**四层建模。** 按 ODS→DWD→DWS→ADS 四层设计了架构，本周落地到 DWD：4 张维度表（dim_user/product/store/date）+ 3 张事实表，订单事实表按天分了 366 个区，EXPLAIN 验证了分区裁剪确实只扫单个分区目录。

**探索性分析。** 基于 DWD 层跑了 13 组查询：全年 GMV 3,626 万、客单价 2,518 元，看了品类、区域、门店、渠道、会员、时间趋势的分布。

## 二、遇到的问题与解决

**1. P99 阈值失效——最有价值的一次"怀疑"。** 操作手册建议用 P99 定异常阈值，我算出来 pay_amount 的 P99 是 551 万——这个"阈值"比绝大多数正常订单大一千倍。排查后发现异常值占比超过 1%，P99 本身已被污染。改用业务区间直方图找断层：金额在 6,000 到 100,000 之间一条记录都没有，正常值和异常值天然分离，取空白带定阈值即可。这件事让我明白：方法论建议都有适用前提，先验证再执行。

**2. 清洗后 6,088 条时间还是不合规。** 行为时间第一次"斜杠转短横线"后做回归校验，发现 6,088 条依旧失败。逐条看样本才知道这批数据是斜杠和缺秒两个问题叠加（`2024/11/14 00:13`），得按长度分档补 `:00`。教训是：清洗脚本必须自带格式回归校验，"改完了"和"改对了"是两回事。

**3. Hive 与 Spark 语法混用。`SEQUENCE()`、`percentile()` 用于 double 列、`GROUP BY 1` 位置引用，三个都是同一类错误——AI 生成的 SQL 混入了 Spark 语法。每个都在真实报错后改成 Hive 等价写法（posexplode 生成日期序列、percentile_approx、子查询包裹）。

**4. 环境问题依旧不断。** 周一开容器全是 Exited(137)，昨晚关机被强杀；推送 GitHub 时 HTTPS 代理 502、SSH 连超两次第三次才成功。

## 三、学习收获

**1. "数据可信"比"数据可用"难一个量级。** 第一周把 CSV 导进去、行数对上就算完成；第二周要让每个字段都经得起追问——枚举为什么这样映射、阈值为什么定在 10000、明细为什么比订单少。修复率 98.87% 这个数字背后，是每一个 0.01% 都能说清口径。

**2. 分析的价值在"反常识"处。** 13 组查询里最值得注意的是会员等级分析：四个等级的 ARPU 极差只有 2.62%，而且普通会员 ARPU 反而最高——等级与消费能力完全脱钩，会员体系没有产生分层价值。如果只看 GMV 总量，这个发现会被平均数掩盖。此外还有 19.28% 的订单未正常履约、区域差异来自用户基数而非客单价，这几条都比"销售额多少"更有经营含义。

**3. 数据的局限性要如实声明。** 分析时发现明细金额合计（6,777 万）与订单金额合计（3,626 万）差了近一倍——源数据两组金额独立生成，没有勾稽关系。我们没有粉饰这个矛盾，而是在简报里明确：品类分析只用相对占比，绝对 GMV 以订单表为准。承认数据边界，比硬给结论更专业。

**4. 设计取舍要留痕。** 架构文档里专门写了"设计取舍记录"：为什么用自然键不用代理键、为什么按天分区（以及它在本数据量下的小文件问题）、为什么价格异常置空而不是删除。这些决策现在不写下来，答辩时自己也说不清当时的理由。
